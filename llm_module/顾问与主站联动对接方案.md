# 顾问与主站联动对接方案(2026-09-03)

> 适用对象: 主站前端(Vue3 `src/`)、主后端(backend :8000)、AI顾问(llm_module :8001)三方联调。
> 本版改动全部落在 **llm_module/**(AI顾问侧, 6 个文件), 主站/主后端**无需改后端接口**, 只需按下面契约做前端渲染/入口/续聊/后台配置。
> nginx 已把 `/api/agents/*` → `llm:8001/agents/*`, `/api/*` → backend:8000, 前端与现有 axios 同一 baseURL(`/api`)即可。
> 所有 `/agents/*` 接口都接受 `Authorization: Bearer <token>`; 未登录照常可用(但取不到用户简历画像, 见②③)。

一句话总结这次做成的 5 件事:
1. 顾问回答自带 **结构化岗位卡片数据**(真实在招岗位, 可点击跳主站岗位详情);
2. 主站任意岗位详情页可"**问顾问**"(把这条 JD 带进对话, 顾问针对该岗+你的简历作答);
3. **历史会话续聊**: 会话/消息落库, 前端可列会话、拉历史、续聊(重启不清零);
4. 顾问出**行业报告/趋势/岗位分析时引用平台在招岗位库数据**, 并标注来源;
5. 后台**管理员可设平台默认大模型**(影响分析/生成类任务, 意图识别仍走廉价路由)。

> ✅ **2026-09-03 补充: 前端联动已在主仓库 `src/` 一并实现**(见文末"前端落地清单"), 下方"队友要接的点"多数已变为"已实现, 供 review"。

## ① 结构化岗位卡片(回答自带真实岗位推荐)

**触发场景**: 登录用户提问且命中 `resume_match / skill_gap / learning_path` 意图、平台简历画像可读时。
**现象**: `POST /agents/chat` 响应顶层新增 `recommended_jobs` 数组(≤6 条)。无简历/非上述意图时为空数组 `[]`, 前端无需特殊兜底。

响应相关字段(顶层, 不受 agent schema 清洗影响):

```jsonc
{
  "session_id": "abc12345",
  "intent": { "intent": "resume_match", "confidence": 0.9 },
  "final_result": { "answer": "...正文回答..." },
  "recommended_jobs": [
    {
      "job_id": 6320,            // 主库 jobs.id, 用于跳转/回填
      "title": "Python高级开发工程师",
      "company": "某某科技",
      "city": "北京",
      "salary": "25000-40000元/月",
      "experience": "3-5年",
      "education": "本科",
      "match_score": 92,          // 基于简历的 LLM 打分; 无简历画像时为 null
      "match_reason": "与您5年Python后端经验匹配..."
    }
  ]
}
```

**队友要接的点(前端)**:
- ChatView 在正文下方把 `recommended_jobs` 渲染成可点卡片; 点击卡片跳主站岗位详情(路由按主站既有 `/jobs/:id`, `job_id` 即该 id), 或把 `{job_id}` 回填进岗位详情页。
- 不要把它写进会话历史文本(它是结构化旁路数据)。

## ② 主站岗位详情页"问顾问"入口

**新能力**: `POST /agents/chat` 的请求体新增可选 `context` 字段, 携带岗位 ID 后顾问会**读取该条真实 JD 并针对它作答**(岗位能力分析 / 与简历做匹配)。

请求体:

```jsonc
{
  "message": "这个岗位和我的匹配度怎么样？",
  "session_id": "可选,续聊时传",
  "context": {
    "job_id": 6320
    // 二选一: 有 job_id 就够(llm 读主库 JD); 拿不到 id 但能拿到 JD 文本时:
    // "jd_text": "岗位职责: ...\n任职要求: ..."
  }
}
```

行为:
- 已登录 + 有简历 → 走 `resume_match`, 用**该岗位真实 JD** 与用户简历逐条比对(薪资/城市/年限/技能), 附 `recommended_jobs`;
- 未登录/无简历 → 走 `job_analysis`, 针对该 JD 做能力拆解与建议。

**队友要接的点(前端)**:
- 岗位详情页放"问顾问"按钮; 点击后 `message` 用一句预设话术(如上面示例), `context: {job_id: <当前岗位id>}`, **带上登录 token**(否则无简历、匹配效果打折), 跳转/展开顾问对话并展示返回。
- `jd_text` 仅当该页确实无 `job_id`(如纯文本 JD 抓取页)时才需要传, 一般不用。

## ③ 历史会话续聊(刷新/重启不清零)

会话与消息落库(llm 私有表 `sessions_db`/`messages`, 随 llm 服务启动自动恢复), 与是否重启无关。

**a) 列我的会话**: `GET /api/agents/sessions`(需登录)
```jsonc
{ "sessions": [
  { "id": "abc12345", "user_id": 2, "industry": "互联网", "role": "job_seeker",
    "message_count": 12, "created_at": "2026-09-03T10:00:00" }
] }
```
只返回"当前登录用户 + 匿名"的会话; 其他人的会话不出现。

**b) 拉某会话完整历史**: `GET /api/agents/sessions/{session_id}/messages?limit=200`(需登录)
- 非本人/不存在 → `403`。
```jsonc
{ "session_id": "abc12345", "user_id": 2,
  "messages": [
    { "id": 101, "role": "user", "content": "...", "intent": "resume_match",
      "created_at": "2026-09-03T10:00:01" },
    { "id": 102, "role": "assistant", "content": "...", "intent": "", "created_at": "..." }
  ] }
```

**c) 续聊**: 拿 `a` 的 `id` 直接当 `session_id` 调 `POST /agents/chat`, llm 会带上该会话历史(超长自动摘要压缩)。

**队友要接的点(前端)**:
- ChatView 加载: 进入对话页先 `GET /agents/sessions` 渲染"历史会话"侧栏 → 点某条用 `b` 拉全文渲染 → 新消息带 `c` 的 `session_id` 续聊。
- 刷新页面后会话不丢, 靠的就是这套(以前前端刷新即清零)。
- 后端注意: JWT 的 `sub`/`user_id` 在 token 里是**字符串**(如 `"2"`); llm 内部已统一转 int 比对所有权, 前端/后端若自己判 owner 也请 `Number()` 后再比, 避免 `2 !== "2"` 误判。

## ④ 行业报告 / 趋势 / 岗位分析引用平台数据

**触发场景**: 意图为 `trend_prediction / report_generation / job_analysis` 时, 顾问 prompt 注入**主库在招岗位库实时统计**(按关键词命中岗位数、城市分布、样本岗位标题)。
**现象**: 回答里出现数字(如"当前平台在招 Python 后端 14 个岗位, 北京最多")时, 句末带 `[数据来源: 主库在招岗位库]` 标注; 不编造未给出的数据。

- 该数字来自主库 `jobs`(在招、未删除), 与主站 ES/岗位列表同一数据源, 前端展示报告无需额外工作。
- **队友注意**: 平台事实注入是 llm 侧已完成; 若主站报告页也想显示"该岗位当前在招 N 个"这类统计, 可直接调主后端现有岗位统计接口, 与顾问引用的口径一致(在招 = `is_deleted=0`)。
- **2026-09-03 标注规则已调优并实测**: 注入 prompt 要求"只在引用数据的句子标注、全文标注 ≤5 处、数据里没有的数字不得编造"。真实趋势报告 E2E 结果: "全国Python后端在招岗位仅14个[数据来源: 主库在招岗位库]，上海7北京5广州2" —— 只有含平台数字的那一句带来源标注, 纯分析段落不标, 无编造数字。

## ⑤ 后台"平台默认大模型"设置(仅管理员)

**a) 查询可用模型 + 当前默认**: `GET /api/agents/models`
```jsonc
{
  "provider": "zhipu",
  "current": "glm-4-flash",          // 管理员设的默认; 未设时=服务基础模型
  "admin_default": "glm-4-flash",
  "available": [
    { "name": "glm-4", "tier": "pro", "cost_per_1k": 0.1, "json_mode": true,
      "tool_call": true, "max_tokens": 4096, "description": "..." }
    // 每个可选模型: name 即 POST 时要传的值
  ],
  "fallback_providers_configured": []
}
```

**b) 设置默认模型**: `POST /api/agents/models/default`, body `{"model": "glm-4"}`(model 取 a 的 name)
- 权限: 角色须为 `admin`/`administrator`/`超级管理员`, 否则 `403`; 未知模型 `400`。
- 生效范围: 分析/生成/回答类任务用新默认模型; **意图识别等轻任务仍走廉价路由**(避免省下的成本反被高频意图识别吃掉)。
- 持久化(llm 运行时表 `model_config`), 重启不丢; 监控接口 `GET /api/agents/model-status` 已带 `default_model`。

**队友要接的点(前端, Admin 页面)**:
- 大模型配置 Tab: 进页 `GET /agents/models` 填充下拉(可展示 tier/成本), 选中项高亮 `current`; 保存调 `POST /agents/models/default`。
- 主站 Account/权限体系里 `role=admin` 的用户才能操作; 普通求职者账号调用会 403, 属预期。
