# 注销留档数据说明（后期处理入口）

> 2026-11-26 新增「注销账号」功能时建立的数据口说明。
> 相关实现：`app/services/user_service.py::delete_account`、`app/models/user.py`、`designs/注销账号.md`。
> 本文只说明**库里留下了什么、怎么查、以后能怎么处理**；当前不包含任何管理端 UI 或定时清理任务。

## 一、口径

- 注销是**软删除**：`users.is_deleted = 1`，账号立即不可登录，主站旧 token 下一次请求即 401。
- **不可恢复**（产品口径）：没有任何找回入口；重新注册是新的 `users` 行（新 `id` / `user_code`），不继承旧账号数据。
- 注销时联系方式**留档后释放**：
  - `phone` / `email` 置 `NULL`，释放 UNIQUE 约束，原手机号/邮箱可重新注册；
  - 原值拷入 `deleted_phone` / `deleted_email`（不设唯一约束，同一联系方式可对应多条注销记录）。
- 关联数据**不级联清理**：简历、投递/收藏、推荐、聊天等原样留在库里，只是随旧 `user_id` 不可达。

## 二、留在了哪些表

| 数据 | 表 | 关联方式 | 现状 |
|---|---|---|---|
| 注销账号主体 | `users` | `id` | `is_deleted=1`；`phone/email=NULL`；`deleted_phone/deleted_email` 留原值；`updated_at` 近似注销时间 |
| 简历（含技能/经历/教育） | `resumes` / `resume_skills` / `resume_experiences` / `resume_educations` | `resumes.user_id`，子表挂 `resume_id` | 保留 |
| 收藏与投递 | `applications` | `user_id` | 保留 |
| 推荐记录 | `recommendations` | `user_id` | 保留 |
| AI 顾问聊天记录 | `chat_history` | `user_id` | 保留 |
| LLM 引擎会话/配额 | `sessions_db`（`messages` 挂 `session_id`）/ `user_quotas` | `user_id` | 保留（LLM 引擎共用同一 MySQL） |

> 全库**没有外键约束**，所以硬删 `users` 行不会报错，只会让上述数据变成孤儿。这也是本期选择软删、不做物理删除的原因。

## 三、常用查询

```sql
-- 1) 某手机号/邮箱的注销历史（按 id 倒序，最新在前）
SELECT id, user_code, nickname, deleted_phone, deleted_email, created_at, updated_at
FROM users
WHERE is_deleted = 1 AND (deleted_phone = '13911110000' OR deleted_email = 'a@b.com')
ORDER BY id DESC;

-- 2) 该联系方式当前是否已重新注册（有结果 = 已重注册）
SELECT id, user_code, nickname, phone, email, onboarded, created_at
FROM users
WHERE is_deleted = 0 AND (phone = '13911110000' OR email = 'a@b.com');

-- 3) 已注销账号列表（updated_at 近似注销时间）
SELECT id, user_code, nickname, deleted_phone, deleted_email, updated_at
FROM users
WHERE is_deleted = 1
ORDER BY updated_at DESC;

-- 4) 某注销账号名下还留了多少关联数据
SELECT
  (SELECT COUNT(*) FROM resumes       WHERE user_id = 16) AS resumes,
  (SELECT COUNT(*) FROM applications  WHERE user_id = 16) AS applications,
  (SELECT COUNT(*) FROM recommendations WHERE user_id = 16) AS recommendations,
  (SELECT COUNT(*) FROM chat_history  WHERE user_id = 16) AS chat_history,
  (SELECT COUNT(*) FROM sessions_db   WHERE user_id = 16) AS llm_sessions,
  (SELECT COUNT(*) FROM user_quotas   WHERE user_id = 16) AS llm_quotas;
```

## 四、后期可做的处理（当前均未实现）

1. **管理端「已注销账号」只读视图**
   - 数据现成：`users WHERE is_deleted=1` + 留档列；可按 `deleted_phone` 精确搜。
   - 目前 `/admin/users` 只查 `is_deleted=0`，注销账号在管理端不可见。
2. **注册时历史提示 / 反作弊**
   - 注册前查 `deleted_phone`/`deleted_email` 是否命中，可提示「该手机号曾注销过账号」或做风控标记。
   - 注意：**不要**据此迁移旧简历/收藏/投递给新账号——产品口径是新账号全新开始。
3. **FR-14 级联物理清理**
   - 按 `user_id` 清理上表（含 LLM 引擎两表，注意 `messages` 要先按 `session_id` 级联）。
   - 建议做成后台任务或运维脚本，先按「注销超过 N 天」筛选，避免误删刚注销的数据。
4. **隐私合规处理**
   - 留档列是明文 PII；如后续有合规要求，可对 `deleted_phone`/`deleted_email` 加密、脱敏或定期清空。
   - 清空留档列不影响账号已注销状态（`is_deleted` 仍是唯一依据）。

## 五、注意事项

- **留档列不唯一**：同一手机号可「注销 → 重注册 → 再注销」产生多条记录，按 `id` / `updated_at` 区分。
- **种子账号别拿来演示注销**：三张种子账号的 `user_code` 会被 `02_seed.sql` 命中，重跑种子不会恢复 `phone/email`（只更新昵称与密码），需手工 `UPDATE` 或重建库。演示建议另建临时号。
- **注销时间没有独立字段**：用 `updated_at` 近似；该行注销后不会再被业务更新，误差可接受。若以后要做精确审计，另加 `deleted_at` 列。
- **LLM 引擎直连接口不校验注销态**：与封禁一致，纯验签不查库；主站接口已全部经 `get_current_user` 拦截。物理合并时统一补。
